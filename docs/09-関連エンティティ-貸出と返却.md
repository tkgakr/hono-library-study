# 09. 関連エンティティ — 利用者と貸出（join・日付・ステータス）

book の縦1本が通ったので、次は**関連を持つエンティティ**に進みます。ここで新しく学ぶのは、book ではまだ出てこなかった3つのパターンです。

1. **日付の変換**: HTTP は ISO 文字列で日付を受け取り、`Date` に変換して下位層へ渡す
2. **ステータスの算出**: 保存された日付から「貸出中／延滞／返却済」を導出する
3. **join 集約レスポンス**: 貸出に紐づく書名・利用者名をまとめて返す

題材は **利用者(member)** と **貸出(loan)** です。member は book とほぼ同型なので差分だけ示し、loan を丁寧に扱います。

```
loan（貸出）
├─ bookId    … どの蔵書を
├─ memberId  … 誰が
├─ loanedOn  … いつ借りて（Date）
├─ dueOn     … いつまでに返す（Date）
└─ returnedOn… いつ返したか（Date | null）← null なら未返却
```

操作は **貸出(create) / 返却(return) / 一覧取得(getList、join あり)** の3つにします。

## 1. 利用者 member（book とほぼ同型・差分のみ）

member は `{ id, name, email, isActive }`。book の `title/author` を `name/email` に置き換えるだけで、4層すべて book と同じ構造です。結果コードは `02` 帯（`W0201`/`E0201`…）を割り当てます。

```ts

  })

// validatedCreateMemberSchema / createMember / ... は book と同じパターンなので省略
```

> member の各層は04〜07章の book を雛形にそのまま写経できます。ここでは loan が member を参照するため「member は存在する」前提で進めます。

## 2. domain: loan モデル `domain/model/loan/loan.ts`

新しいのは **日付フィールドと、日付をまたいだ `refine`** です。

```ts
// src/api/domain/model/loan/loan.ts
import type { CalendarDate } from '@core/core'
import z from 'zod'

export const loanSaveOperations = {
  CREATE: 'create',
  RETURN: 'return',
} as const

// ステータスは保存された日付から算出する派生値（DBには持たない）
export const loanStatuses = {
  ON_LOAN: 'onLoan', // 貸出中
  OVERDUE: 'overdue', // 延滞
  RETURNED: 'returned', // 返却済
} as const
export type LoanStatus = (typeof loanStatuses)[keyof typeof loanStatuses]

// DB から取得した1件
export const getLoanSchema = z
  .object({
    id: z.uuid(),
    bookId: z.uuid(),
    memberId: z.uuid(),
    loanedOn: z.date(),
    dueOn: z.date(),
    returnedOn: z.date().nullable(),
  })
  .brand<'GetLoan'>()
export type GetLoan = z.infer<typeof getLoanSchema>

// (1) 貸出：返却期限は貸出日以降でなければならない（日付をまたぐ refine）
export const validatedCreateLoanSchema = z
  .object({
    bookId: z.uuid(),
    memberId: z.uuid(),
    loanedOn: z.date(),
    dueOn: z.date(),
  })
  .refine((data) => data.dueOn.getTime() >= data.loanedOn.getTime(), {
    message: '返却期限は貸出日以降にしてください',
    path: ['dueOn'],
  })
  .brand<'ValidatedCreateLoan'>()
export type ValidatedCreateLoan = z.infer<typeof validatedCreateLoanSchema>

export const createdLoanSchema = z
  .object({
    operation: z.literal(loanSaveOperations.CREATE),
    id: z.uuid(),
    bookId: z.uuid(),
    memberId: z.uuid(),
    loanedOn: z.date(),
    dueOn: z.date(),
  })
  .brand<'CreatedLoan'>()
export type CreatedLoan = z.infer<typeof createdLoanSchema>

export const createLoan = (entity: ValidatedCreateLoan): CreatedLoan =>
  createdLoanSchema.parse({ operation: loanSaveOperations.CREATE, id: crypto.randomUUID(), ...entity })

// (2) 返却：返却日を記録する
export const returnedLoanSchema = z
  .object({
    operation: z.literal(loanSaveOperations.RETURN),
    id: z.uuid(),
    returnedOn: z.date(),
  })
  .brand<'ReturnedLoan'>()
export type ReturnedLoan = z.infer<typeof returnedLoanSchema>

export const returnLoan = (id: string, returnedOn: Date): ReturnedLoan =>
  returnedLoanSchema.parse({ operation: loanSaveOperations.RETURN, id, returnedOn })

export type SaveLoan = CreatedLoan | ReturnedLoan

// (3) ステータス算出：保存値（日付）からドメインのルールで導く純粋関数
// ステータス判定に必要なのは2つの日付だけ。GetLoan 全体を要求すると、
// 一覧の join 行のように id/bookId/memberId を持たない呼び出し側が値を捏造することになるため、
// 引数は「必要な入力」だけに絞る。
export type LoanStatusSource = Pick<GetLoan, 'dueOn' | 'returnedOn'>

// 延滞は「返却期限を過ぎている」＝ 期限当日は延滞ではない、という日単位の判定。
// today を CalendarDate で受けることで、時刻付きの `new Date()` をそのまま渡して
// 期限当日を延滞と誤判定する事故を型で防ぐ。現在時刻をどこで読むかは呼び出し側の責務。
export const resolveLoanStatus = (loan: LoanStatusSource, today: CalendarDate): LoanStatus => {
  if (loan.returnedOn !== null) return loanStatuses.RETURNED
  return loan.dueOn.getTime() < today.getTime() ? loanStatuses.OVERDUE : loanStatuses.ON_LOAN
}
```

ポイント:
- **日付は domain では `Date` で扱う**（`z.date()`）。文字列ではない。文字列⇄Date の変換は interface 層の責務（後述）。
- **`refine` で日付の前後関係を検証**（`dueOn >= loanedOn`）。book の「どちらか必須」より一歩進んだクロスフィールド検証。
- **`resolveLoanStatus` は純粋関数**。DB にステータス列は持たず、`returnedOn` と `dueOn` から毎回導出する。`today` を引数で受けて決定的にする（テストしやすい）。
- **引数はエンティティ全体ではなく「判定に必要な入力」だけ**にする（`Pick` で表現）。`GetLoan` を要求してしまうと、一覧の join 行のように `bookId`/`memberId` を持たない呼び出し側が、通すためだけにダミー値を詰める羽目になります。「この関数が本当に何に依存しているか」がシグネチャに出るのも利点です。

**日付比較は「暦日」に揃える**。`date` 型カラムは drizzle が `new Date('2026-07-06')`（= UTC 0 時）として返す一方、`new Date()` は時刻を持ちます。この2つを素朴に `<` で比べると、**期限当日の朝から延滞扱いになる**バグが出ます。比較の前に現在時刻を暦日へ落とすヘルパーを用意します。

```ts
// src/api/core/core.ts
// 「時刻を持たない暦日」を表す型。実体は Date だが、toCalendarDate() でしか作れない。
// 日付比較の引数をこの型で受けておけば、時刻付きの `new Date()` の混入を型で防げる。
declare const calendarDateBrand: unique symbol
export type CalendarDate = Date & { readonly [calendarDateBrand]: true }

// 時刻を持つ「瞬間」を、その暦日の 0 時（UTC）だけを持つ Date に正規化する。
// 暦日の判定はローカルタイムゾーン（本アプリは TZ=Asia/Tokyo）で行う。
export const toCalendarDate = (instant: Date): CalendarDate =>
  new Date(Date.UTC(instant.getFullYear(), instant.getMonth(), instant.getDate())) as CalendarDate
```

「日付だけを持つ値」と「時刻を持つ瞬間」は別物、というのは日付を扱うコードで最も踏みやすい落とし穴です。境界（DB から取り出した直後・現在時刻を作った直後）でどちらの表現なのかを揃えてから比較します。

**この区別を型に載せる**のが `CalendarDate` です。zod の `.brand()` と同じ発想で、実体は `Date` のままシグネチャだけを別物にします。こうしておくと `resolveLoanStatus(loan, new Date())` はコンパイルエラーになり、正規化を通った値しか渡せません。

```
error TS2345: Argument of type 'Date' is not assignable to parameter of type 'CalendarDate'.
```

> コメントで「暦日を渡すこと」と書くだけでは、いずれ誰かが破ります。**規約は型にすると守られます**。

## 3. domain: 集約レスポンス型とリポジトリ契約

一覧では「貸出 + 書名 + 利用者名 + ステータス」をまとめて返したい。これを**集約レスポンス型**として domain に定義します。

```ts
// src/api/domain/model/loan/loanListItem.ts
import { z } from 'zod'
import { loanStatuses } from '@domain/model/loan/loan'

// 一覧の1行（join 済みの集約ビュー）
export const loanListItemSchema = z
  .object({
    id: z.uuid(),
    bookTitle: z.string(),
    memberName: z.string(),
    loanedOn: z.date(),
    dueOn: z.date(),
    returnedOn: z.date().nullable(),
    status: z.enum([loanStatuses.ON_LOAN, loanStatuses.OVERDUE, loanStatuses.RETURNED]),
  })
  .brand<'LoanListItem'>()
export type LoanListItem = z.infer<typeof loanListItemSchema>
```

```ts
// src/api/domain/repository/loan/loanRepository.ts
import type { CalendarDate } from '@core/core'
import type { GetLoan, SaveLoan } from '@domain/model/loan/loan'
import type { LoanListItem } from '@domain/model/loan/loanListItem'
import type { ValidatedGetListLoanSearchConditions } from '@domain/model/loan/loanSearchConditions'
import type { EntityData, ListData } from '@domain/model/generic/repositoryData'

export interface ILoanRepository {
  // join 集約。ステータスの算出に使う「今日」は呼び出し側から受け取る（時計を infrastructure に持たせない）
  fetchListWithRelations: (
    today: CalendarDate,
    searchConditions: ValidatedGetListLoanSearchConditions,
  ) => Promise<ListData<LoanListItem>>
  fetchDetail: (id: string) => Promise<EntityData<GetLoan>>
  save: (command: SaveLoan) => Promise<boolean>
}
```

> 一覧（join 済みの表示用ビュー）と詳細（生の `GetLoan`）で返す型が異なる点に注目。表示集約は `LoanListItem`、業務ロジック用は `GetLoan` と使い分けます。

検索条件は book と同じ骨格（`parameters` / `paging` / `sort`）です。貸出は「この利用者の貸出だけ」「この蔵書の貸出履歴だけ」を見たくなるので、その2つを絞り込み条件にします。

```ts
// src/api/domain/model/loan/loanSearchConditions.ts
// 貸出一覧の絞り込み条件。どちらも実カラムなので where 句は素直に組める。
const validatedGetListLoanParametersSchema = z.object({
  bookId: z.uuid().optional(),
  memberId: z.uuid().optional(),
})
export type ValidatedGetListLoanParameters = z.infer<typeof validatedGetListLoanParametersSchema>

export const validatedGetListLoanSearchConditionsSchema = z
  .object({
    parameters: validatedGetListLoanParametersSchema.optional(),
    paging: validatedSearchConditionPagingSchema,
    sort: validatedSearchConditionSortSchema,
  })
  .brand<'ValidatedGetListLoanSearchConditions'>()
```

> **`status` を絞り込み条件に入れていない**のは意図的です。`status` は DB に持たない派生値なので、where 句で絞るには `resolveLoanStatus` と同じ判定ルール（`returned_on is null and due_on < $today` など）を SQL 側にもう一度書くことになります。ドメインのルールが2箇所に分かれると、片方だけ直して食い違うのが定番の事故です。どうしても必要なら「ルールが二重化している」と認識した上で入れるか、ステータスを列として保存する（＝派生値をやめる）設計に切り替えます。

**「今日」を引数で受けている**のも設計上の判断です。ステータスの算出には現在時刻が要りますが、`fetchListWithRelations` の中で `new Date()` を呼ぶと、リポジトリの返す値が実行時刻に依存して**テストで固定できなくなります**。時計は副作用なので、DB アクセスと同じく外から渡します（[10章](./10-テスト-レイヤー別.md) でここが効いてきます）。

現在時刻を実際に読むのは application 層（usecase）です。

```ts
// src/api/application/usecase/loan/loanGetListUsecase.ts （抜粋）
export const loanGetListUsecase = async (
  repository: ILoanRepository,
  logger: ILogger,
): Promise<Result<ListData<LoanListItem>, OperationResult>> => {
  // 時計を読むのはここ1箇所。テストでは固定日を渡した repository スタブを使う
  return ResultAsync.fromPromise(
    repository.fetchListWithRelations(toCalendarDate(new Date())),
    promiseErrorReturn(logger, ResultCodes.LOAN_LIST_FAILED),
  )
}
```

## 4. infrastructure: loan テーブルと join 取得

テーブルは book/member への外部キーを持ちます。一覧取得で **book/member を join** し、ステータスを算出して `LoanListItem` に組み立てます。

**外部キー制約は `references()` で明示します**。これは単なる飾りではなく、`innerJoin` の前提を DB に保証させるためのものです。制約が無いと、蔵書や利用者を物理削除したときに参照先を失った貸出行が残り、`innerJoin` は**その行を結果から落とします**。つまり「貸出記録が一覧から消える」という、最も気づきにくい形のデータ欠落になります。

```ts
// src/api/infrastructure/database/model/loan/loan.ts （抜粋）
import bookTable from '@infrastructure/database/model/book/book'
import { defaultTimestamps, primaryId } from '@infrastructure/database/model/generic/commonColumns'
import memberTable from '@infrastructure/database/model/member/member'
import { date, pgTable, uuid } from 'drizzle-orm/pg-core'

const columns = {
  ...defaultTimestamps,
  id: primaryId,
  // 外部キー制約を付けて、参照先の無い貸出（孤立行）が生まれないことを DB に保証させる。
  // これがないと、蔵書や利用者を物理削除したときに innerJoin で貸出行そのものが一覧から消える。
  bookId: uuid()
    .notNull()
    .references(() => bookTable.id),
  memberId: uuid()
    .notNull()
    .references(() => memberTable.id),
  loanedOn: date({ mode: 'date' }).notNull(),
  dueOn: date({ mode: 'date' }).notNull(),
  returnedOn: date({ mode: 'date' }), // nullable
} as const

export const loanTableConfig = { name: 'loan', columns }
const loanTable = pgTable(loanTableConfig.name, columns)
export default loanTable

// ソート可能カラム（クエリのカラム名 → 実カラム）
export const sortablePgColumnMap: SortablePgColumnMap = {
  loaned_on: loanTable.loanedOn,
  due_on: loanTable.dueOn,
  returned_on: loanTable.returnedOn,
  created_at: loanTable.createdAt,
} as const
// insert/return の parse 関数（createInsertSchema / createUpdateSchema）は book と同じパターンで作る
```

`bun run db:generate` すると、次のマイグレーションが出ます（`ON DELETE no action` = 貸出されている蔵書の削除は DB が拒否する）。

```sql
-- 0003_add_loan_foreign_keys.sql
ALTER TABLE "loan" ADD CONSTRAINT "loan_book_id_book_id_fk"
  FOREIGN KEY ("book_id") REFERENCES "public"."book"("id") ON DELETE no action ON UPDATE no action;
ALTER TABLE "loan" ADD CONSTRAINT "loan_member_id_member_id_fk"
  FOREIGN KEY ("member_id") REFERENCES "public"."member"("id") ON DELETE no action ON UPDATE no action;
```

> 本アプリに物理削除の経路はなく、蔵書・利用者は `isActive` による論理削除だけです。それでも制約を付けるのは、**「アプリが正しく動く限り起きない」ことと「起きえない」ことは別**だからです。手作業の SQL や将来の削除機能で壊れる余地を、DB 側で閉じておきます。
>
> なお `leftJoin` にして「参照先が無くても貸出行は残す」方針もあり得ますが、その場合は `bookTitle`/`memberName` を nullable にして表示側に分岐を増やすことになります。**起きないケースのための分岐を永久に抱える**ことになるため、ここでは制約で防ぐ側を選びました。

```ts
// src/api/infrastructure/database/repository/loanRepository.ts （fetchListWithRelations 抜粋）
import type { CalendarDate } from '@core/core'
import { getDbInstance } from '@infrastructure/database/dbAccess'
import loanTable from '@infrastructure/database/model/loan/loan'
import bookTable from '@infrastructure/database/model/book/book'
import memberTable from '@infrastructure/database/model/member/member'
import { loanListItemSchema } from '@domain/model/loan/loanListItem'
import { resolveLoanStatus } from '@domain/model/loan/loan'
import { addLimitOffset, addOrderBy } from '@infrastructure/database/repository/genericRepository'
import { and, count, eq } from 'drizzle-orm'

const fetchListWithRelations = async (
  today: CalendarDate,
  searchConditions: ValidatedGetListLoanSearchConditions,
) => {
  const db = getDbInstance()
  // join して必要なカラムだけ取得（DTO 投影）
  let baseQuery = db
    .select({
      id: loanTable.id,
      bookTitle: bookTable.title,
      memberName: memberTable.name,
      loanedOn: loanTable.loanedOn,
      dueOn: loanTable.dueOn,
      returnedOn: loanTable.returnedOn,
    })
    .from(loanTable)
    .innerJoin(bookTable, eq(loanTable.bookId, bookTable.id))
    .innerJoin(memberTable, eq(loanTable.memberId, memberTable.id))
    .where(buildGetListWhereConditions(searchConditions.parameters))
    .$dynamic()
  baseQuery = addOrderBy(baseQuery, searchConditions.sort, sortablePgColumnMap)
  baseQuery = addLimitOffset(baseQuery, searchConditions.paging)
  const rows = await baseQuery

  // total は絞り込み後の全件数。ページングを外した同じ条件で数える（join も同じに揃える）
  const countDto = await db
    .select({ count: count(loanTable.id) })
    .from(loanTable)
    .innerJoin(bookTable, eq(loanTable.bookId, bookTable.id))
    .innerJoin(memberTable, eq(loanTable.memberId, memberTable.id))
    .where(buildGetListWhereConditions(searchConditions.parameters))
  const total = countDto[0]?.count ?? 0

  // 取得した行に、ドメイン関数で算出したステータスを足して集約レスポンス型にする
  const value = rows.map((row) => loanListItemSchema.parse({ ...row, status: resolveLoanStatus(row, today) }))
  return { value, total }
}

// 一覧の where 句を、指定されたパラメータだけから動的に組み立てる（book と同じ形）
const buildGetListWhereConditions = (parameters?: ValidatedGetListLoanParameters): SQL | undefined => {
  if (!parameters) return undefined
  const filters: SQL[] = []
  if (parameters.bookId) filters.push(eq(loanTable.bookId, parameters.bookId))
  if (parameters.memberId) filters.push(eq(loanTable.memberId, parameters.memberId))
  return filters.length > 0 ? and(...filters) : undefined
}
```

ポイント:
- **`total` は「ページングを外した、同じ絞り込み条件での件数」**。`value.length` ではありません（それでは1ページ分の件数になってしまう）。件数クエリでも **join を本体と同じに揃える**のを忘れないでください。`innerJoin` は結合先が無い行を落とすため、join を省くと件数だけが多くなります。
- **ソートは `sortablePgColumnMap` のホワイトリスト経由**（loan テーブル側に定義）。クエリ文字列のカラム名をそのまま SQL に渡さないので、任意の列でソートを仕込まれません。マップに無い名前は `addOrderBy` が黙って無視します。
- **select の投影が、そのまま集約レスポンスの形になっている**。`resolveLoanStatus` の引数を `LoanStatusSource`（＝ `dueOn` と `returnedOn` だけ）にしてあるので、join 行 `row` をそのまま渡せます。判定に使わない `bookId`/`memberId` を select する必要も、ダミー値を詰めて `as never` でごまかす必要もありません。
- ステータスは取得時に `resolveLoanStatus` で算出して埋める。DB には持たない。
- 境界で `loanListItemSchema.parse()`。投影した列＋`status` が過不足なく揃っていることは、ここで検証されます。

> 「取得した DTO をドメイン型へ組み立て直してから返す」のが join 取得の定石ですが、**組み立て直す先はいつも完全なエンティティとは限りません**。一覧に必要なのは表示用の集約（`LoanListItem`）であって `GetLoan` ではないので、`GetLoan` を経由させると「通すためだけの値」が生まれます。詳細取得（`fetchDetail`）のほうは業務ロジック用に `GetLoan` を返す、という使い分けです。

保存側（`save`）は「操作ごとに文を切り替える」形です。loan の操作は貸出と返却の2つで、**返却の update には `returnedOn IS NULL` を付けます**。

```ts
// src/api/infrastructure/database/repository/loanRepository.ts （save の中身）
// 操作ごとに文を切り替える。operation が増えたら default で型エラーになる
switch (command.operation) {
  case loanSaveOperations.CREATE: {
    const result = await trx.insert(loanTable).values(createLoanParsedSchema.insertSchema(command)).returning()
    return result.length > 0
  }
  case loanSaveOperations.RETURN: {
    // 返却は未返却の行だけを対象にする（二重返却を DB 側で弾き、更新0件 = false になる）
    const result = await trx
      .update(loanTable)
      .set(createLoanParsedSchema.returnSchema(command))
      .where(and(eq(loanTable.id, command.id), isNull(loanTable.returnedOn)))
      .returning()
    return result.length > 0
  }
  default:
    return assertNever(command)
}
```

**`if (CREATE) {...}` で早期 return して「残りは返却だろう」と書かない**のがポイントです。今は union が2つなので動きますが、将来 `RENEW`（延長）のような操作が増えたとき、**黙って返却の update に落ちます**。`switch` + `assertNever` にしておけば、その瞬間にコンパイルエラーで気づけます。

```ts
// src/api/core/core.ts
// switch の網羅漏れをコンパイル時に検出するための番人。
// 全ケースを処理していれば引数は never に絞られ、union にケースが増えた瞬間に型エラーになる。
export const assertNever = (value: never): never => {
  throw new Error(`未対応の値です: ${JSON.stringify(value)}`)
}
```

> book（`save` の操作が4つ）では、`let setValues: ...` を宣言してから `switch` で代入し、その後に1回だけ update する形を採っています。あちらは**どの操作も「update で、set の中身だけ違う」**ため。loan は貸出が insert、返却が update と**文そのものが違う**ので、`switch` の各 case で完結させています。「代入を網羅する」か「文を網羅する」かの違いで、どちらも網羅漏れは型で検出できます。

`id` だけで更新すると、すでに返却済みの貸出にも update が成功して `returnedOn` を上書きしてしまいます。**「未返却のものだけ返却できる」という状態遷移の条件を where に畳み込む**のが定石で、こうすると「対象がなかった」＝「更新0件」＝ `false` と自然に表現できます。

> このチェックは application 層（`loanCheckService` で事前に状態を確認する）でも書けますが、確認と更新の間に別のリクエストが割り込む余地が残ります。**更新条件そのものに含めておけば、その隙間がなくなります**（`UPDATE ... WHERE` は 1 文で原子的に評価されるため）。事前チェックは「利用者に理由を返す」ため、where の条件は「不正な状態にしない」ためと、役割を分けて両方書くのが実務的です。

## 5. application: 貸出ユースケース（日付は受け取るだけ）

usecase は book と同じ neverthrow パターン。日付は既に `Date` に変換されて渡ってくるので、ビジネスルール（例：同じ蔵書が貸出中でないか）に集中します。

```ts
// src/api/application/usecase/loan/loanCreateUsecase.ts （抜粋）
export const loanCreateUsecase = async (
  repository: ILoanRepository,
  logger: ILogger,
  validatedEntity: ValidatedCreateLoan,

  return ok(createLoan(validatedEntity))
    .asyncAndThen((created) => ResultAsync.fromPromise(repository.save(created), promiseErrorReturn(logger, ResultCodes.LOAN_SAVE_FAILED)))

}
```

## 6. interface: ISO 文字列 ⇄ Date の変換（最重要ポイント）

ここが book との一番の違いです。**HTTP では日付を ISO 文字列で受け取り、`validate*()` で `Date` に変換**してから domain へ渡します。

```ts
// src/api/interface/model/loan.ts （作成部分の抜粋）
import { z } from '@hono/zod-openapi'
import { validatedCreateLoanSchema } from '@domain/model/loan/loan'
import type { ValidatedCreateLoan } from '@domain/model/loan/loan'

// 生の HTTP：日付は ISO 文字列で受ける
export const unValidatedCreateLoanSchema = z
  .object({
    bookId: z.uuid().openapi({ example: '...' }),
    memberId: z.uuid().openapi({ example: '...' }),
    loanedOn: z.iso.date().openapi({ description: '貸出日(YYYY-MM-DD)', example: '2026-06-22' }),
    dueOn: z.iso.date().openapi({ description: '返却期限(YYYY-MM-DD)', example: '2026-07-06' }),
  })
  .brand<'UnValidatedCreateLoan'>()
export type UnValidatedCreateLoan = z.infer<typeof unValidatedCreateLoanSchema>

// 継ぎ目：文字列 → Date に変換してから domain の parse へ
export const validateCreateLoan = (request: UnValidatedCreateLoan): ValidatedCreateLoan =>
  validatedCreateLoanSchema.parse({
    bookId: request.bookId,
    memberId: request.memberId,
    loanedOn: new Date(request.loanedOn),
    dueOn: new Date(request.dueOn),
  })
```

レスポンス側は逆に、`Date` を ISO 文字列に整形して返します（`LoanListItem` を JSON 化する `formatLoanListResponse` のような変換関数を model に置くのが定石）。

```ts
// 例：レスポンス整形（Date → ISO 文字列、status はそのまま）
export const formatLoanListItem = (item: LoanListItem) => ({
  ...item,
  loanedOn: item.loanedOn.toISOString().slice(0, 10),
  dueOn: item.dueOn.toISOString().slice(0, 10),
  returnedOn: item.returnedOn ? item.returnedOn.toISOString().slice(0, 10) : null,
})
```

ルーター（`createRoute` + `openapi`）と集約は book と同じ形なので省略します。`GET /loans` を叩くと、書名・利用者名・算出済みステータス付きの一覧が返ります。

## この章のまとめ

新しく学んだ3パターン:

| パターン | どの層で | 要点 |
| --- | --- | --- |
| 日付変換 | interface | HTTP は ISO 文字列 / domain は `Date`。`validate*()` で変換、レスポンスで逆変換 |
| ステータス算出 | domain | DB に持たず、`resolveLoanStatus` の純粋関数で日付から導出。`today` を引数化 |
| join 集約 | infrastructure | join した DTO をドメイン型へ組み立て、`LoanListItem` で境界 parse |
| クロスフィールド検証 | domain | `refine` で `dueOn >= loanedOn` |

book で学んだ4層の骨格は完全に再利用しつつ、関連・日付・派生値という現実的な複雑さを足せました。次章では、ここまで作った各層に**テスト**を書きます。
